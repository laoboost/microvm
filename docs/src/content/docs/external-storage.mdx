Sandboxes are ephemeral by design. If you need durable workspace state across sandbox lifecycles, mount your own cloud or network storage into the sandbox.

The platform handles mounting on the host and bind-mounts the result into your sandbox. Your image needs no special mount tooling, and credentials never enter the sandbox.

## How it works

1. Declare mounts in the create request. The platform validates the spec and stores credentials encrypted at rest.
2. At sandbox start, the platform establishes the mount on the host and makes it available inside the sandbox at the path you specified.
3. On `Stop`, the mount is torn down. On `Start`, it is re-established. After a host reboot, mounts are restored automatically on the next sandbox start.

## Supported mount types

| Type | Source format | Host binary used | Credentials field |
|---|---|---|---|
| `s3` | `s3://bucket[/prefix]` or `bucket` | `mount-s3` | `access_key_id`, `secret_access_key`, `session_token` |
| `nfs` | `host:/exports/path` | `mount.nfs` | none |
| `sshfs` | `user@host:/path` | `sshfs` | `private_key_pem` |
| `rclone` | `remote:path` | `rclone mount` | `rclone_conf` |

Up to 8 mounts per sandbox are supported, with up to 32 credential keys and 4 KiB total payload.

## S3 mount options

The S3 adapter accepts structured option keys on the mount spec's `options` map:

| Key | Value | mount-s3 flag |
|---|---|---|
| `uid` | positive integer (must be ≥ 1) | `--uid` |
| `gid` | positive integer (must be ≥ 1) | `--gid` |
| `allow_other` | `"true"` / `"1"` | `--allow-other` |
| `allow_overwrite` | `"true"` / `"1"` | `--allow-overwrite` |

The daemon pins `--prefix`, `--endpoint-url`, `--profile`, `--region`, and
`--read-only` itself; `options.extra_args` is split into argv tokens and any
flag from that pinned set is rejected (mount-s3 errors on duplicate flags
rather than taking the last one, so the denylist is the only conflict
protection). Duplicate flags inside `extra_args` are also rejected. If any
structured key is set, `--uid`/`--gid`/`--allow-other`/`--allow-overwrite` are
additionally denied in `extra_args` — mixing a structured key with the same
flag in `extra_args` fails closed; the legacy path with no structured keys
still accepts those flags in `extra_args` (deprecated).

The `endpoint` option must be an absolute `http://` or `https://` URL; other
values (including bare hosts) are rejected at spec validation instead of
failing inside mount-s3.

Mount `source` values must not begin with `-` for any mount type, so a
source can never be parsed as a flag by the host-side mount tool.

## Security Model

- Credentials never enter the sandbox.
- Credentials are encrypted at rest with AES-256-GCM.
- Read APIs return `has_credentials: true` but never the actual values.
- Mount fields are passed to host-side mount tools (`mount`, `mount-s3`, `sshfs`, `rclone`) running as the daemon user, outside the sandbox isolation boundary. Sources are checked against a dash-prefix guard, S3 `extra_args` is filtered through a denylist of daemon-pinned flags, and the S3 endpoint must be an absolute `http(s)://` URL. The platform assumes PAT holders are host operators; the guards are hardening, not a tenant boundary.

## Operational Notes

- Mounts are established at `Create` and re-established at `Start`.
- A failed mount is retried once before being disabled.
- Host requirements include `fuse3`, `sshfs`, `nfs-common`, `rclone`, and AWS `mountpoint-s3`.
- Network egress blocking applies inside the sandbox, not to the host mount process.
